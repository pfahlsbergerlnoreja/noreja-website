Projected output

Process deviations. Real systems don't follow the happy path perfectly. Define rules that randomly mess up some cases:
· Overjump — skip a slot entirely (e.g. orders that never get invoiced).
· Wrong order — swap two slots' timestamps (e.g. invoice dated before its order).
· Rework — insert a duplicate row for a slot with a later timestamp (e.g. revised invoice).
· Abort — the case reaches this slot, but everything AFTER it (this whole branch onward) never happens (e.g. an order that's placed but never processed further). Unlike Overjump, which only skips one single slot, Abort cuts off the rest of the chain from here on, unconditionally — works on ANY table, with or without a status column.
↳ Not the same as "Drop-off %" on a status column (Schritt 01): Drop-off % only shapes that table's OWN stage sequence — it stops nothing downstream by itself (see the note under Drop-off % there). Abort is the guaranteed "nothing happens after this point" lever, for status AND ordinary tables alike. Caveat: if the target slot feeds an AND/XOR join only via "Join wartet auf" (not a direct chain step), Abort currently only removes the target slot's own successors — it does not yet reach past that join. Target the join's own slot instead if you need the cascade to continue beyond it.

Angehakt (Standard, wie bisher): alle nachfolgenden Aktivitäten des Falls verschieben sich um die Nacharbeitsdauer — passend, wenn die Nacharbeit den weiteren Fall wirklich verzögert. Abgehakt: nichts sonst ändert sich — weder spätere Stufen derselben Tabelle noch nachfolgende Aktivitäten bleiben stehen, nur der Änderungs-Zeitstempel wird gesetzt. Wichtig für Noreja-Sichtbarkeit: ein Rework wird nur erkannt, wenn der Änderungs-Zeitstempel NACH der nächsten Aktivität im Fall liegt — bei abgehaktem Mitverschieben also einen ausreichend großen Rework-Gap eintragen (größer als der übliche Abstand bis zur nächsten Aktivität), sonst bleibt die Änderung für die Prozessanalyse unsichtbar.
Ohne Status-Spalte: erzeugt eine ECHTE neue Zeile in derselben Tabelle (z. B. eine geänderte Bestellung nochmal angelegt), statt nur das Änderungsdatum auf der bestehenden Zeile zu setzen — unabhängig davon, ob zusätzlich eine Log-Tabelle konfiguriert ist. Mit Status-Spalte (siehe unten „Nur diese Stufe(n) anfassen"): dupliziert das ganze benannte Stufen-Fenster statt nur ein Änderungsdatum zu setzen.
Bei einer Status-Spalte: nichts angehakt = wie bisher nur die zuletzt erreichte Stufe. Angehakt = genau diese Stufen-Zeile(n) dieses Falls bekommen das Änderungsdatum bzw. werden dupliziert; liegen dazwischen weitere Stufen (die nicht explizit angehakt wurden), werden diese automatisch mit eingeschlossen — der ganze Bereich von der ersten bis zur letzten angehakten Stufe gilt als „berührt". Alle SPÄTER erreichten Stufen derselben Statusfolge werden zusätzlich zu den nachfolgenden Prozessschritten um die Nacharbeitsdauer verschoben. Fälle, die diese Stufe(n) nie erreicht haben, bleiben unberührt.
