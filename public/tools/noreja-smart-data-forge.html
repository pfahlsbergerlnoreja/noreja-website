Projected output

Process deviations. Real systems don't follow the happy path perfectly. Define rules that randomly mess up some cases:
· Overjump — skip a slot entirely (e.g. orders that never get invoiced).
· Wrong order — swap two slots' timestamps (e.g. invoice dated before its order).
· Rework — insert a duplicate row for a slot with a later timestamp (e.g. revised invoice).
· Abort — the case reaches this slot, but everything AFTER it (this whole branch onward) never happens (e.g. an order that's placed but never processed further). Unlike Overjump, which only skips one single slot, Abort cuts off the rest of the chain from here on, unconditionally — works on ANY table, with or without a status column.
↳ Not the same as "Drop-off %" on a status column (Step 01): Drop-off % only shapes that table's OWN stage sequence — it stops nothing downstream by itself (see the note under Drop-off % there). Abort is the guaranteed "nothing happens after this point" lever, for status AND ordinary tables alike. Caveat: if the target slot feeds an AND/XOR join only via "Join waits for" (not a direct chain step), Abort currently only removes the target slot's own successors — it does not yet reach past that join. Target the join's own slot instead if you need the cascade to continue beyond it.

Marks the rework as its own event (e.g. bestellung_geaendert_am) — only for the affected cases. The column should be set up in Step 01 as optional/"mostly NULL" (nullPct 100%) so that unchanged cases get no value.
Checked (default, as before): all subsequent activities of the case shift by the rework duration — appropriate when the rework really delays the rest of the case. Unchecked: nothing else changes — neither later stages of the same table nor subsequent activities move, only the change timestamp is set. Important for Noreja visibility: a rework is only detected if the change timestamp lies AFTER the next activity in the case — so with shifting unchecked, enter a sufficiently large rework gap (larger than the usual interval to the next activity), otherwise the change stays invisible to process analysis.
Without a status column: creates a REAL new row in the same table (e.g. a changed order created again), instead of just setting the change date on the existing row — regardless of whether a log table is additionally configured. With a status column (see "Only touch these stage(s)" below): duplicates the whole named stage window instead of just setting a change date.
With a status column: nothing checked = as before, only the last stage reached. Checked = exactly these stage row(s) of this case get the change date or get duplicated; if further stages lie in between (not explicitly checked), they are automatically included — the whole range from the first to the last checked stage counts as "touched". All stages of the same status sequence reached LATER are also shifted, along with subsequent process steps, by the rework duration. Cases that never reached these stage(s) remain untouched.
