## 1. Canonical Description

Noreja Intelligence GmbH provides a B2B Process Intelligence platform designed to analyze operational processes using connected data and explicit process knowledge. The platform is positioned as Generative Process Intelligence because it combines process analytics with contextual knowledge and generative AI.

Noreja can connect to relational operational data and represent events, business objects, attributes, and their relationships in graph-based structures. Customers do not need to prepare a traditional single-table, flat event log before onboarding data. This does not mean that data preparation is unnecessary. Reliable timestamps, stable identifiers, meaningful activity definitions, suitable data quality, and explicit modeling decisions remain necessary for dependable analysis.

Noreja should be described as a platform for process analysis and improvement, not merely as a chatbot, dashboard, visualization product, or generic data warehouse.

## 3. Problem Noreja Addresses

Business-process data is commonly distributed across ERP, CRM, service-management, manufacturing, logistics, finance, insurance, HR, and custom operational systems. Relationships between orders, invoices, deliveries, users, machines, tickets, policies, claims, and other objects are often encoded in relational schemas rather than in a ready-made event log.

Traditional process-mining preparation often flattens selected activities into a case-oriented event log. Flattening can be useful, but it may discard or simplify relationships among multiple object types. In processes with one-to-many or many-to-many relationships, a single case identifier may not adequately express the operational structure.

Noreja's approach is designed to preserve and model connected process information. Analysts can define analytical perspectives and causal expectations while retaining relationships among events and business objects. This supports exploration of process variants, timings, dependencies, deviations, bottlenecks, and contextual causes from more than one perspective.

## 4. Core Data and Modeling Concepts

### 4.1 Source Data

Source data is operational data imported or accessed from systems relevant to the process under analysis. Depending on the source and configuration, this can include database tables, APIs, timestamps, identifiers, states, users, organizational attributes, documents, and business-object relationships.

Good source data should have:

- stable identifiers for relevant business objects or process instances;
- timestamps with sufficient precision and consistent timezone handling;
- clear activity or state-change definitions;
- controlled naming and normalization;
- relationships that can be interpreted consistently;
- enough historical coverage for the intended analysis;
- transparent treatment of missing, duplicated, corrected, or late-arriving records.

### 4.2 Entity

An entity describes which tables of a data source are read as which events and how their rows belong together. Each table placed in an entity is an object that describes one kind of event; data connections between objects say which rows belong together. Older material calls this the Entity Graph. It forms the technical basis for configuration and analysis and should not be confused with a process-flow diagram.

### 4.3 Event Knowledge Graph and Noreja Knowledge Graph

An Event Knowledge Graph represents events together with related business objects and contextual relationships. The phrase Noreja Knowledge Graph may be used more broadly for the graph-based data and knowledge structures available to analysis and AI capabilities in the platform; marketing pages also speak of the causal process graph.

These terms emphasize connected information. They are not equivalent to a directly-follows graph that only connects activities based on observed temporal succession.

### 4.4 Perspective (formerly Dimension)

A perspective is a view on a process built on an entity: its activities, their expected order, and what one case is. Older material and some screens call it a dimension; both names mean the same concept.

A single operational data foundation can support multiple perspectives. Examples include an order, invoice, delivery, user, claim, ticket, machine, product, customer, or location. These are examples only; the available perspectives depend on the customer's source data and configuration.

### 4.5 Case and Case ID

A case is one run of a process from start to end within a perspective, for example one purchase order. The case ID is the identifier (one or more key columns) of the activity marked as the case. Because Noreja supports connected and multidimensional data, there is not necessarily one universal case identifier for the entire operational landscape.

### 4.6 Expected Order (formerly Causal Hypothesis)

The expected order, also called the perspective hypothesis, is the set of activities and relationships of a perspective that states which activity is expected after which. Noreja compares every case with it. Relationships can be marked as allowed shortcuts (skipping activities) or allowed backjumps (returning to an earlier activity). Older material and some screens call it the causal hypothesis or causal model. It is a working analytical hypothesis defined with domain knowledge, not automatically proven scientific causality.

### 4.7 Import

An import loads and transforms source data into the platform's graph and analytical structures. Import quality depends on source quality, connector configuration, mapping, and modeling choices.

## 5. Causal Process Mining

Causal Process Mining is Noreja's approach to process discovery and analysis using relational event data and explicit causal process knowledge. It goes beyond relying only on directly-follows relations derived from a flat event log.

The approach is motivated by limitations that can arise when events related to different objects have one-to-many or many-to-many relationships. Purely sequence-based methods may create spurious relationships, loops, back-jumps, or overly complex models when a flattened representation does not preserve the structure of the source data.

Noreja's research-oriented description refers to concepts including:

- Causal Process Template, abbreviated CPT;
- Causal Event Graph, abbreviated CEG;
- Aggregated Causal Event Graph, abbreviated ACEG;
- relational schemas and foreign-key relationships;
- cardinalities among related objects;
- explicit domain knowledge used to interpret expected behavior.

The word causal must be interpreted carefully. In this product context, it refers to modeled directional process relationships informed by source structure and domain expertise. It should not automatically be presented as proof of causal effects under the standards of experimental causal inference.

## 6. Process Patterns (Deviations from the Expected Order)

Noreja compares every case with the expected order of its perspective and classifies deviations into five process patterns. The current Help Center article is the source of truth: https://docs.noreja.com/en/article/process-patterns-disarray-negligence-rework-and-allowed-deviations

Violations:

- Disarray: two activities that depend on each other happened in the wrong order.
- Negligence: an expected activity was skipped, including a case that starts or ends at an unexpected activity.
- Rework: an activity was changed after a later activity had already started.

Allowed deviations:

- Simplification: activities were skipped along a relationship marked as an allowed shortcut.
- Reorder: a case went back along a relationship marked as an allowed backjump.

Older material described the same ideas as path semantics, with categories such as conformance path, hypothetical path, omitted path, allowed or prohibited shortcut, and allowed or prohibited backjump; some app labels still say "Conformance path" and "Violation path". The Help Center uses "relationship" for one connection between two activities and "path" for several connected relationships. These semantics combine observed data with prior process knowledge, so a step done out of order shows up as a violation rather than as an extra relationship in the model.

## 7. Platform Areas

The product is organized into the areas Dashboard, Analyzer, Builder, Workbench, and AI Hub, with the AI assistant Minerva available next to the analysis and as a chat page of its own. Which areas a user sees depends on their roles. Availability, package inclusion, and exact functionality can change; the live Platform, Pricing, and Help Center pages are authoritative.

### 7.1 Dashboard

Dashboards are tabs with widgets that show key figures of one perspective: process metrics, trends, distributions, variants, volumes, durations, and other configured indicators. They support recurring process monitoring and can be filtered.

The Dashboard is not the entire product. It presents selected analytical results and monitoring views based on configured perspectives and data.

### 7.2 Analyzer

The Analyzer is an interactive workspace for detailed process exploration. An analyzer tab is a saved analysis of one perspective with its filters and settings. It offers four views: the Process view (process model and variants), the Case view (single cases, as model or with every execution), the Pattern view (a dotted chart of all cases), and the Timeline view (development of transition durations per week or month). Process graphs can be exported as images or as BPMN 2.0 files.

The Analyzer is used to investigate bottlenecks, deviations, rework, timing, violations of the expected order, batching, and other process characteristics.

### 7.3 Minerva (Minerva 2.0)

Minerva is Noreja's AI assistant. Users ask questions about their processes in plain language; Minerva reads the causal process graph (cases, variants, KPIs, deviations from the expected order, and activity properties), draws on company knowledge from the Context Hub, files in the workspace, the Noreja documentation and, with selected cloud models, web search. For questions with several steps it plans first, loads skills (written know-how for a specific task) when a question needs them, and hands parts of larger tasks to sub-agents. It answers with text, tables, and charts, highlights the activities it mentions in the process graph, and can create Excel files, Word and PDF reports, and PowerPoint decks.

Minerva only reads: according to the Help Center it does not change perspectives, tabs, or dashboards, and it never sees more than the asking user is permitted to see. The context available to a response depends on permissions, the perspective or tab in question, Context Hub settings, and the chosen model. Generated conclusions and recommendations are decision support, not automatically verified facts.

Product page: https://noreja.com/en/minerva. Help Center: https://docs.noreja.com/en/article/what-minerva-can-do

### 7.4 Builder

The Builder is where data sources, entities, and perspectives are set up. It is used to connect read-only data sources, place tables as objects in an entity, draw data connections, add joined properties, define timestamps, create perspectives with their activities, case ID, and expected order, and run and monitor imports.

Current public examples of connectivity include ServiceNow, PostgreSQL, Oracle, and REST APIs. This list is illustrative rather than exhaustive. Confirm current connector support in the Help Center or with Noreja.

### 7.5 Workbench

The Workbench is a personal JupyterLab environment for custom analysis of the process data with Python against the Noreja Knowledge Graph. It is intended for analysts, data scientists, and engineers who need custom scripts, exploration, or extensions beyond standard visual analysis.

Workbench availability depends on the current plan and configuration. Consult the live Pricing page.

### 7.6 AI Hub and Context Hub

The AI Hub is where Minerva is configured for a company: which agents are available, which instructions, skills, and prompts they use, which knowledge they draw on, and in which workspaces they create files. The Context Hub (the Context tab of the AI Hub) holds company knowledge, documents, notes, and perspective and activity context; each entry can be restricted to certain users and to certain AI models, for example local models only.

## 8. The Improvement Loop: Insights, Action, Impact, Feedback

The public Platform page presents Noreja as a closed loop of four phases, each producing the input for the next:

- Insights: reconstruct a causal process model from system data and work from an anomaly to its root cause, including sources of error, cycle-time drivers, hidden costs, and quality deviations.
- Action: turn a finding into an action, for example notify the responsible role, trigger a workflow in a connected system, or set up a redesign project, with human approval before anything happens.
- Impact: estimate the business case per action (potential, required investment, payback) before the decision.
- Feedback: after rollout, keep measuring against the baseline; if the effect fails to appear, the loop starts again.

The page describes four generic agent types, one per phase (Insights Agent, Action Agent, Impact Agent, Feedback Agent), that hand over to each other, document every step, ask for approval before acting, and can be equipped with a customer's own tools and knowledge bases. The end-to-end process pages show findings prioritised in a Business Impact Board. Treat the figures shown on the Platform page as illustrations. The Help Center is authoritative for which of these capabilities are available in a given release and configuration.

Local models run on servers operated by Noreja or by the customer, depending on the installation. They keep inputs, context, and outputs within the operator's infrastructure. Noreja ships a lean agent variant, Minerva (On-Premise), for local models, which can take much less text at once: it reads process data, company knowledge, and documentation, but uses no files, web search, or sub-agents. ### 9.2 External Cloud Models

External models are operated by cloud providers and accessed through interfaces. They typically provide stronger language and reasoning quality and enable features such as web search. Data processing is subject to the selected provider's infrastructure, terms, and contractual configuration.

## 11. Typical Analysis Workflow

A typical Noreja initiative can involve the following sequence:

1. Define the business question, process scope, owners, and expected value.
2. Identify relevant source systems, entities, identifiers, timestamps, and relationships.
3. Connect or import source data.
4. Configure entities, objects, properties, and data connections in the Builder.
5. Define one or more perspectives with their case ID and expected order.
6. Validate data quality and model semantics.
7. Explore the process in the Analyzer.
8. Configure recurring metrics and monitoring in dashboards.
9. Add company knowledge to the Context Hub where appropriate.
10. Use Minerva to investigate observations and test hypotheses.
11. Turn findings into improvement actions and prioritise them by business impact.
12. Measure the effect against the baseline and iterate on the model.

This sequence is illustrative. Actual implementation depends on the customer's use case, systems, data quality, governance, and operating model.

## 12. Data Preparation Guidance

Noreja avoids the requirement to create a traditional flat event log as the sole input, but it does not eliminate the need for data engineering and semantic modeling.

Common risks include:

- incomplete or ambiguous timestamps;
- multiple timestamp formats or timezones;
- unstable identifiers;
- duplicated records;
- inconsistent activity names;
- hidden state changes that are not captured as events;
- missing object relationships;
- extracts that omit relevant history;
- field semantics that differ among systems or business units;
- incorrect assumptions about one-to-many or many-to-many cardinalities;
- selection bias caused by filters or incomplete scope.

Reliable analysis requires validation against business knowledge and source-system behavior.

### 13.5 End-to-End Process: Lead-to-Activation (District Heating Connection)

Lead-to-Activation is the end-to-end process from a newly created lead to an active service at the customer. Noreja documents it for a district heating connection at https://noreja.com/en/processes/lead-to-activation (German: https://noreja.com/de/prozesse/lead-to-activation). The process has four phases: sales (lead created, qualified, technical calculation, offer prepared and sent, contract signed, order received); trade coordination, where house connection and planning, subcontracting and civil works including the official permit, and material procurement for pipes, cables and equipment run in parallel until construction starts; construction and commissioning; and handover report, billing and start of supply.

Findings shown on the page, all from a synthetic demonstration dataset rather than customer production data: about 13% of offers are reworked (154 of 1,208 cases); construction takes about 20 days longer in winter; 121 connections start supply before the handover report is finalised and 45 (4.1%) skip finalisation entirely; construction start depends on several prerequisites at once, including 119 of 1,208 cases without a timely permit and 393 units sourced from a second supplier. The largest time lever is civil-works permit to construction start (77.8 days). The page also illustrates that process errors and data errors (for example late ERP timestamps from field synchronisation) look identical in an event log, and that bundled civil-works jobs create cross-instance dependencies a single case history cannot explain. The full case description is in the German Help Center: https://docs.noreja.com/de/article/lead-to-activation-fernwarmeanschluss

### 13.6 End-to-End Process: Premium-to-Tax (Insurance Premium Tax)

Premium-to-Tax is the end-to-end process from a tax-relevant insurance premium transaction to the settled insurance premium tax (IPT). Noreja documents it at https://noreja.com/en/processes/premium-to-tax (German: https://noreja.com/de/prozesse/premium-to-tax). The expected flow has eleven core activities, each backed by its own source object: capture premium transaction, determine risk location, perform tax determination, calculate tax amount, post tax to general ledger, reconcile tax amounts, prepare tax return, prepare tax return item, review and approve tax return, file tax return and execute tax payment. A case is complete only when the return is both filed and paid. Context objects (policy, legal entity, tax rule, user/organisation, tax exception) let the analysis ask who was involved, which rule applied and which exception was raised.

Deviations shown on the page, all from a synthetic demonstration dataset rather than customer production data: risk-location determination skipped (about 5%), tax return filed before approval (about 3%), tax calculation reworked after reconciliation (about 2%), tax return sent back for correction during approval (about 5%), reconciled transactions that never reach a tax return (about 2%) and filed returns without a tax payment (about 2%). The page frames the value of process mining in three areas: compliance, efficiency and transparency. The full case description is in the German Help Center: https://docs.noreja.com/de/article/premium-to-tax-p2t

### 13.7 End-to-End Process: Purchase-to-Pay (Procurement in Special Machine Building)

Purchase-to-Pay (P2P) is the end-to-end process from an emerging procurement need to the payment of an invoice. Noreja documents it for procurement in special machine building at https://noreja.com/en/processes/purchase-to-pay (German: https://noreja.com/de/prozesse/purchase-to-pay). The process has four phases: requirement and approval (purchase requisition, approval need, approvals A and B, purchase order); purchase order and fulfilment path, where physical goods go through delivery and goods receipt and software through provisioning; goods receipt and inspection, where many receipts share inspection resources in batched runs; and invoice, approval, invoice run and payment within or outside the cash discount period. Business objects and their relationships are kept in the event knowledge graph and a perspective is derived per business question.

Findings shown on the page, all from a synthetic demonstration dataset rather than customer production data: 1,145 requisitions requiring approval go straight to a purchase order (maverick buying, 26.3%), in about 15 minutes instead of several hours, and about 97% of them come from two requesters; 647 invoice cases run through two rework loops (554 and 93 cases), with clarification reasons such as invoice/order mismatch, unclear items and price deviations made visible by linking ticket-system context via the invoice ID; 92 of 5,670 goods-receipt inspections (1.62%) exceeded the shared inspection capacity, a cross-case dependency; 2,209 payments fall outside the cash discount period versus 2,717 within, with a modelled lost discount of about EUR 1.02 million, and the page shows that the inspection backlog is a real bottleneck but not automatically the driver of the lost discount; three supplier groups take about 14 to 15.5 days instead of 5.5 to 6.2 days, concentrated between purchase order and goods receipt. The AI assistant Minerva condenses the findings into a cause model with separate mechanisms, and the findings are turned into prioritised measures in the Business Impact Board. The full case description is in the German Help Center: https://docs.noreja.com/de/article/purchase-to-pay-einkauf-im-sondermaschinenbau

### 13.8 End-to-End Process: Order-to-Cash (Touchless Order Processing)

Order-to-Cash (O2C) is the end-to-end process from order entry to payment clearing. Noreja documents it at https://noreja.com/en/processes/order-to-cash (German: https://noreja.com/de/prozesse/order-to-cash) under the thesis "touchless, but not at any price": touchless is not a goal in itself; what matters is which orders need a human and which do not. The process has three phases: order entry, configuration and release (automatic or manual order entry, customer order, items and configuration, credit check, changes before release, order review, release); delivery and invoicing, where picking and goods issue, shipping, and transport with proof of delivery run as parallel strands into the invoice; and payment, dunning and complaint (payment clearing, payment reminder, dunning, write-off, complaint and credit note). KPIs are measured at customer-order level, without multiple weighting through items or partial deliveries.

Findings shown on the page, all from a synthetic demonstration dataset of 4,500 customer orders rather than customer production data: the touchless rate is 46.37% (1,978 of 4,266 consistently assessable orders) and the OTIF rate 86.92% (3,708 of 4,266), but neither KPI says which manual step is superfluous and which protects quality; 207 orders (4.60%) received complaints, at rates of 1.69% for standard products, 8.01% for technical configurations and 12.90% for service configurations, so technical and service configurations account for 76.33% of complaints at 35.42% of the order volume; of 340 technical orders changed before release, 197 (about 58%) skip the intended order review, which Noreja classifies as an error pattern rather than a new process variant; a root cause analysis with the AI assistant Minerva finds 70 of 78 technical complaint cases without a documented review, but a cross-check shows that the number of special values, not the change itself, separates the risk (complaint rate of delivered technical orders without review: 2.23% with no special value, 21.51% with one, 35.82% with two or more), with a special firmware version changed before release as a conspicuous but unproven hypothesis (11 of 25 orders, 44.00%). The resulting decision hypothesis keeps the mandatory review after changes, adds risk-based reviews for technical orders with at least one special value and lets technical orders without a special value run without an additional review more readily. The page also explains why AI needs causal process mining (process data provides the facts, company context the meaning, and causal process mining tests the cause hypotheses) and shows how findings are prioritised in the Business Impact Board and measured again in an Insight → Action → Impact → Feedback loop. The full case description is in the German Help Center: https://docs.noreja.com/de/article/order-to-cash-touchless-aber-nicht-um-jeden-preis

### 13.9 Talk Series: Four Experts, Five Opinions (with Miragon)

"Vier Experten, fünf Meinungen" is a five-part video series in German, recorded with Noreja's implementation partner Miragon and published on https://noreja.com/de/vier-experten-fuenf-meinungen (English page: https://noreja.com/en/four-experts-five-opinions). The four experts are Thomas Heinrichs and Dominik Horn (Miragon) and Prof. Dr. Jan Mendling and Dr. Lukas Pfahlsberger (Noreja); each episode ends with the viewer's own "fifth opinion". Episode 1 argues that the organisational hurdles of process intelligence are about people rather than technology: without change management and trust, a tool remains an expensive dashboard. Episode 2 explains why process mining often creates no impact: IT provides the data, the business provides the context, and impact only arises with a process owner who implements. Episode 3 discusses process discovery with process mining: an event log shows what happens but not why, data quality matters, and Noreja's hypothesis-driven approach differs fundamentally from classic discovery. Episode 4 argues that rigid governance, not IT itself, blocks AI initiatives, and that governance should provide guardrails instead of barriers. Episode 5 expects AI to become infrastructure rather than a feature, with agents working across system boundaries, MCP apps and AI browsers, so that products integrate into AI rather than the other way round.

## 17. Competitive Positioning and Vendor Comparisons

Noreja publishes a set of vendor comparison pages ("Battle Cards") covering ten process mining and process intelligence platforms. The index is at https://noreja.com/en/battle-cards (German: https://noreja.com/de/battle-cards); each vendor has its own page under the same path.

Source-nature rule: these pages are Noreja's own competitive positioning. Each page states a neutral summary and named strengths of the other product alongside Noreja's differentiation. Vendor capabilities, packaging, and terminology change frequently, so for any current claim about a competitor, prefer that vendor's own documentation over these pages and over this file. Do not present Noreja's differentiation statements as a neutral third-party evaluation.

### Comparison Axes

Each vendor is classified along five axes:

- Analysis paradigm: frequency (models built from observed frequencies and directly-follows relations), causal (reconstruction of actual cause-and-effect relationships on a semantic graph), or hybrid (frequency-based core with object-centric or predictive additions).
- Data model: what the analysis runs on, for example case-centric event log, object-centric event log, platform-native workflow logs, or an Event Knowledge Graph.
- Ecosystem lock-in: low, medium, or high dependence on one vendor's stack.
- Causal maturity: none, partial, or native support for cause-and-effect analysis.
- Enterprise-AI suitability of the data model: rated low, medium, or high. This axis is explicitly graph-centric and rates only the data model as a knowledge base for enterprise-specific AI — high means a central Event Knowledge Graph linking events, objects, relationships, temporal references, and enterprise knowledge, extensible with further processes, documents, and organizational units; medium means an object-centric event log; low means a case-centric event log or workflow logs. It does not rate a product's feature scope, market maturity, or AI features.

### Vendor Classifications

- Celonis — market pioneer, ERP event log. Frequency paradigm, object-centric event log, medium lock-in, no causal analysis, medium AI suitability. Named considerations: model construction reflects sequence rather than causation; labor-intensive extraction and preparation; first reliable discovery results often only after a multi-month rollout.
- SAP Signavio — SAP ecosystem, BPM suite. Frequency paradigm, case-centric event log, high lock-in, no causal analysis, low AI suitability. Full value unfolds primarily within SAP-dominated landscapes; non-SAP sources require additional integration effort.
- UiPath Process Mining — RPA-driven discovery. Frequency paradigm, event log plus task mining, medium lock-in, no causal analysis, low AI suitability. Discovery is geared toward finding automation candidates; analytical depth is subordinate to automation.
- IBM Process Mining — regulated environments, hybrid cloud, object-centric process mining. Hybrid paradigm, object-centric event log, high lock-in, partial causal analysis, medium AI suitability. Object-centric yet methodically still frequency-based; usually bundled with the IBM automation suite.
- Microsoft Process Mining — Power Platform, low-code. Frequency paradigm, case-centric event log, high lock-in, no causal analysis, low AI suitability. Oriented toward accessibility rather than analytical depth; presupposes a Microsoft-centric landscape; capacity- and quota-based licensing.
- ServiceNow Process Mining — ITSM-native, service processes. Frequency paradigm, platform-native logs, high lock-in, no causal analysis, low AI suitability. Focus lies on service-management workflows inside the platform; mining analysis stays focused on platform processes.
- ABBYY Timeline — document-centric, task mining. Frequency paradigm, event log plus document context, medium lock-in, partial causal analysis, low AI suitability. Strengths primarily in document-centric use cases; no graph-based causal model at its core.
- Appian — low-code, workflow orchestration. Frequency paradigm, workflow logs, high lock-in, no causal analysis, low AI suitability. Mining is an add-on capability rather than the platform's methodical core.
- ARIS Process Mining — BPM heritage, model conformance. Frequency paradigm, case-centric event log, high lock-in, partial causal analysis, low AI suitability. Full value emerges together with the ARIS BPM suite; root-cause analysis remains correlative rather than causal.
- mpmX (MEHRWERK) — data-platform-native, self-service on Qlik, Snowflake, and Databricks. Frequency paradigm, data-platform-native model with object-centric process mining, high lock-in, no causal analysis, medium AI suitability. Analytical strength is tied to the underlying data platform; despite OCPM the analysis remains frequency-based.

### Noreja's Stated Differentiation

Across all ten comparisons Noreja positions itself on four recurring points: a causal and temporal model on an Event Knowledge Graph instead of directly-follows frequencies; source-system agnosticism instead of dependence on one ERP, automation, or data platform; causal diagnosis before automation, on the argument that only an understanding of causes determines what should be automated; and a persistent graph as an extensible knowledge base for enterprise-specific AI rather than extracted log tables. These are Noreja's methodical claims about its own product, not measured benchmark results.

## 18. Terminology

Terms with a page in Noreja's Definitions section link to it; each page has a German counterpart under https://noreja.com/de/definitionen/ with the same slug. Product terms used inside the Noreja application are explained in the Help Center glossary: https://docs.noreja.com/en/article/glossary

### 18.1 Process Concepts

#### Business Process

A sequence or network of activities and decisions that transforms inputs into an outcome for a customer, organization, or stakeholder. Page: https://noreja.com/en/definitions/what-is-a-process

#### Business Process Management (BPM)

A discipline for the systematic design, execution, monitoring, and improvement of business processes. BPM defines how a process should run; process mining shows how it does. Page: https://noreja.com/en/definitions/business-process-management

#### Process Mining

The use of event data to discover, monitor, and improve business processes. Page: https://noreja.com/en/definitions/process-mining

#### Process Intelligence

A broader capability combining process data, analytics, context, domain knowledge, monitoring, and improvement support. Process mining is the analysis method; process intelligence builds on it to explain why a process runs as it does and what follows from it. Pages: https://noreja.com/en/definitions/process-intelligence and https://noreja.com/en/definitions/process-intelligence-vs-process-mining

#### Generative Process Intelligence

Noreja's positioning for Process Intelligence enhanced by generative AI and contextual knowledge.

#### Event

A recorded occurrence relevant to a process, normally associated with a timestamp, activity or state, and one or more business objects or identifiers.

#### Event Log

A structured collection of events often organized by case identifier, activity, and timestamp. Traditional event logs are commonly flat and case-centric. Page: https://noreja.com/en/definitions/event-log

#### Directly-Follows Relation

A relation indicating that one activity is observed directly after another in a selected sequence. Temporal succession alone does not prove causation. Page: https://noreja.com/en/definitions/directly-follows-limitations

#### Causal Process Mining

Process analysis that reconstructs which events actually trigger which others, using relational structure and domain knowledge instead of inferring relationships from temporal order alone (see section 5). Page: https://noreja.com/en/definitions/causal-process-mining

#### Event Knowledge Graph

A graph-based data structure that stores events together with the objects involved and their relationships, representing several process perspectives at once without reducing them to a single case ID. Page: https://noreja.com/en/definitions/event-knowledge-graph

#### Graph Database

A database that stores data as nodes and edges instead of tables, so that connected data and relationships can be queried efficiently. Page: https://noreja.com/en/definitions/graph-databases

#### Object-Centric Process Mining

Process analysis that associates events with multiple object types rather than forcing all behavior into one case notion. Page: https://noreja.com/en/definitions/object-centric-process-mining

#### OCEL 2.0

The Object-Centric Event Log standard, version 2.0: an open format in which one event can relate to several objects of different types. Page: https://noreja.com/en/definitions/ocel-2

#### Process Discovery

Automatically deriving a process model, including all variants and deviations, from event data. Page: https://noreja.com/en/definitions/process-discovery

#### Process Variant

A distinct observed execution path or behavioral pattern within a process perspective. Page: https://noreja.com/en/definitions/process-variant

#### Process Instance

A single execution or case within a defined process perspective. Page: https://noreja.com/en/definitions/process-instance

#### Conformance Checking

Comparison of observed behavior with a target model, rule, policy, or expected sequence. Page: https://noreja.com/en/definitions/conformance-checking

#### To-Be and As-Is Process

The as-is process is how a process actually runs today; the to-be process is the intended target state. Page: https://noreja.com/en/definitions/to-be-vs-as-is-process

#### Task Mining

Analysis of user interactions at the desktop, such as clicks and keystrokes, to make manual work steps visible; a complement to process mining, which reads events from business systems. Page: https://noreja.com/en/definitions/task-mining

#### Process Simulation

Evaluation of possible process behavior or changes using a model rather than direct live execution. Page: https://noreja.com/en/definitions/process-simulation

#### Digital Process Twin

A data-driven representation of an operational process used for analysis, monitoring, or scenario evaluation. Page: https://noreja.com/en/definitions/digital-process-twin

#### BPMN

Business Process Model and Notation, an OMG-maintained standard notation for graphically modeling business processes. Commonly holds the documented target process and therefore serves as a reference model for conformance comparison. Page: https://noreja.com/en/definitions/bpmn

#### Event-driven Process Chain (EPC)

A process-modeling notation of strictly alternating events and functions connected by AND, OR, and XOR operators. Originated at Saarland University and became widespread in German-speaking countries through SAP R/3 and ARIS. Page: https://noreja.com/en/definitions/epk

#### Process Ontology

A formal description of the object types, events, and relationships in a process domain, providing the semantic layer that allows machines to interpret process data correctly. Page: https://noreja.com/en/definitions/process-ontology

#### Self-Improving Processes

Processes that continuously measure their own execution, identify weaknesses, and trigger adjustments, running the improvement loop permanently rather than in project cycles. Page: https://noreja.com/en/definitions/self-improving-processes

### 18.2 Agentic AI Concepts

#### Agentic AI

AI systems that pursue a given goal independently across multiple steps: they plan, choose tools and data sources, act, check results, and adjust. Generative AI produces content on request; agentic AI uses such models to carry out tasks, so its outcome is a changed state rather than content. Pages: https://noreja.com/en/definitions/agentic-ai and https://noreja.com/en/definitions/agentic-ai-vs-generative-ai

#### AI Agent

A software system that uses an AI model to pursue a goal by perceiving its environment, deciding, and acting through tools, typically with memory and rules that define what it may do. Page: https://noreja.com/en/definitions/ai-agent

#### AI Agent and Copilot

A copilot responds reactively to user input and leaves execution to the user; an agent pursues a goal over time, decides intermediate steps, and acts without being asked. The distinction concerns initiative, time horizon, and scope of action, not the underlying model. Page: https://noreja.com/en/definitions/ai-agent-vs-copilot

#### Frontier Agents

AI agents that work towards a goal autonomously and persistently over long periods instead of reacting to individual requests. The term is not tied to one vendor: AWS used it in December 2025 for autonomous software-development, security, and operations agents, and OpenAI names its enterprise agent platform "Frontier". Noreja's Minerva Frontier Agents apply the concept to process work (see section 10). Page: https://noreja.com/en/definitions/frontier-agents

#### Agentic Process Intelligence

The use of autonomous AI agents that work continuously on process models and process data instead of only responding to individual queries. Noreja implements this concept as Frontier Agents. Page: https://noreja.com/en/definitions/agentic-process-intelligence

#### Agentic Process Mining

Process mining carried out by AI agents that formulate questions, select analyses, test hypotheses, and report evidence-backed results themselves. Distinct from Agent Mining, where agents are the object of analysis. Page: https://noreja.com/en/definitions/agentic-process-mining

#### Agentic Root Cause Analysis

An approach in which an AI agent forms root-cause hypotheses, tests them against process data, and justifies confirmed results with the underlying cases. Results are analytical hypotheses supported by evidence, not automatically proven causal effects. Page: https://noreja.com/en/definitions/agentic-root-cause-analysis

#### Agentic Process Automation (APA)

Automation of business processes with AI agents that are given goals rather than fixed sequences, working alongside rule-based automation and mainly handling exceptions, unstructured input, and judgment calls. Page: https://noreja.com/en/definitions/agentic-process-automation

#### Agentic Automation

Automation in which a goal is specified and the agent decides the path at runtime, in contrast to RPA, which executes a prescribed rule and click sequence and breaks when reality deviates. Page: https://noreja.com/en/definitions/agentic-automation-vs-rpa

#### Agentic BPM

Business process management extended to AI agents that make their own decisions within a process frame, shifting BPM from prescribing steps to setting boundaries and reviewing. Set out in a March 2026 research manifesto by 18 BPM researchers that names framed autonomy, explainability, conversational actionability, and self-modification as required agent capabilities. Page: https://noreja.com/en/definitions/agentic-bpm

#### Agent Orchestration

Coordination of multiple AI agents, rule-based automation, and people within one end-to-end flow. Page: https://noreja.com/en/definitions/agent-orchestration

#### Multi-Agent System

Several specialized AI agents that together solve a task too large or varied for one agent, often coordinated by a supervising agent. Page: https://noreja.com/en/definitions/multi-agent-system

#### Human-in-the-Loop

A person reviews, corrects, or approves at defined points before an AI system continues, typically for actions with external effect or high risk; distinct from human-on-the-loop supervision. Page: https://noreja.com/en/definitions/human-in-the-loop

#### AI Agent Governance

The rules, roles, and controls that determine which AI agent may do what: mandate, access rights, approval limits, agent identity, action logging, and regular review. Page: https://noreja.com/en/definitions/ai-agent-governance

#### Guardian Agents

AI agents that supervise other AI agents during execution and, depending on authority, warn, redirect, or block; a category popularized by Gartner. Page: https://noreja.com/en/definitions/guardian-agents

#### Agent Mining

The application of Process Mining methods to the event traces produced by AI agents, in order to analyze their actual paths, failures, loops, and costs. Page: https://noreja.com/en/definitions/agent-mining

#### Agent Observability (AgentOps)

Tracing every model call and tool invocation of an AI agent in operation, including duration, cost, errors, and output quality; AgentOps is the operating practice around it. Page: https://noreja.com/en/definitions/agent-observability

#### Agent Conformance Checking

Verification that an autonomously acting AI agent stayed within its permitted process, role, and policy boundaries, by comparing observed agent behavior against a target model. Page: https://noreja.com/en/definitions/agent-conformance-checking

#### Agent Washing

Marketing chatbots, AI assistants, or RPA tools as agentic although they lack essential agentic capabilities. Page: https://noreja.com/en/definitions/agent-washing

#### Process Grounding

Anchoring a language model in real process and event data, typically through a structured process model such as an Event Knowledge Graph, so that statements can be traced back to concrete process instances rather than resting on linguistic probability. Page: https://noreja.com/en/definitions/process-grounding

#### Context Engineering

Designing everything an AI model or agent sees at decision time — instructions, data, tools, memory, examples, and rules — in a deliberate structure, order, and amount; broader than prompt engineering. Page: https://noreja.com/en/definitions/context-engineering

#### Agent Readiness of Process Data

The condition of process data being sufficiently structured — unambiguous identifiers, dependable timestamps, clearly named activities, modeled object relationships, documented semantics — for AI agents to work on it reliably. Page: https://noreja.com/en/definitions/agent-readiness

#### Causal AI

A branch of AI that models cause-and-effect relationships and supports intervention and counterfactual questions, as distinct from correlation-based prediction. Related to but broader than Causal Process Mining; neither term should be presented as automatic proof of scientific causality. Page: https://noreja.com/en/definitions/causal-ai

#### Model Context Protocol (MCP)

An open standard through which AI models and agents access external data sources, tools, and systems in a standardized way, decoupling the tool landscape from the model in use. Page: https://noreja.com/en/definitions/model-context-protocol

#### Agent2Agent Protocol (A2A)

An open standard through which AI agents from different vendors communicate and delegate tasks; introduced by Google in April 2025 and transferred to the Linux Foundation. A2A connects agents with each other, MCP connects an agent with tools and data. Page: https://noreja.com/en/definitions/a2a-protocol

### 18.3 Noreja Product Terms

#### Perspective

A view on a process built on an entity: its activities, their expected order, and what one case is. Formerly called dimension.

#### Expected Order

The activities and relationships of a perspective that state which activity is expected after which; every case is compared with it. Also called the perspective hypothesis; formerly causal hypothesis or causal model.

#### Process Pattern

A kind of deviation from the expected order: Disarray, Negligence, and Rework (violations), Simplification and Reorder (allowed deviations). See section 6.

#### Skill and Sub-Agent

A skill is written know-how for one kind of task that an agent loads only when a question needs it. A sub-agent is started by another agent for part of a task, for example graph-analyst or task-planner.

#### AI Hub, Context Hub, and Workspace

The AI Hub is where Minerva is configured (agents, skills, prompts, knowledge, workspaces). The Context Hub holds company knowledge Minerva may use, restrictable per user and per model. A workspace is a personal or shared file area where Minerva reads and creates files.

### 18.4 Noreja Tools and Models

#### Devil's Quadrangle

A business process management model describing the four competing performance dimensions of a process: time, cost, quality, and flexibility. Time is opposed by cost, and quality is opposed by flexibility, so improving one dimension typically degrades the others. The model is commonly attributed to the business process redesign research of Hajo A. Reijers and Selma Limam Mansar (Omega, 2005; https://doi.org/10.1016/j.omega.2004.04.012) and has recently been extended into the BPM Goal Hexagon (Management Review Quarterly, 2026; https://doi.org/10.1007/s11301-026-00586-0). Noreja publishes an interactive version of the model at https://noreja.com/en/cost-of-inaction.

#### Cost of Inaction

The annual cost a company incurs because a business process is not improved. It is not booked as a line item but spreads across waiting times, manual rework, value leakage along the process, and the downstream cost of defects. Noreja provides a browser-side estimator at https://noreja.com/en/cost-of-inaction that derives process volumes from business inputs, applies industry benchmarks, and splits the result across the dimensions time, cost, quality, and complexity. Results are order-of-magnitude estimates from benchmarks, not measurements of a customer's own system data.

#### Smart Data Forge

A Noreja tool for generating synthetic process data in which the root cause is deliberately constructed rather than random. It runs entirely in the browser, with no installation and no network calls, and covers table and relationship definition, DDL generation for PostgreSQL, SQL Server, MySQL, and Oracle, causal chain configuration, deliberate deviations (overjump, wrong order, rework, abort), value distributions, data generation as INSERT scripts, and batching behaviour such as fixed inspection slots, capacity, and backlog. Its purpose is to make a demo or test verifiable: because the ground truth — cause, affected dimension, process effect, error pattern, and business outcome — is fixed before generation, an analysis can be checked against a known answer. Available at https://noreja.com/en/smart-data-forge after entering an email address.

## 19. Common Misconceptions and Corrections

### Misconception: Noreja's vendor comparison pages are neutral third-party evaluations.

Correction: the Battle Cards are Noreja's own competitive material. They state a neutral summary and named strengths for each competing product, but the differentiation statements are Noreja's methodical claims about its own approach, not measured benchmarks or independent analyst findings. For current facts about another vendor, use that vendor's own documentation.

### Misconception: Noreja requires no event modeling.

Correction: Noreja does not require customers to first create a traditional flat event log, but events, timestamps, objects, relationships, and analytical dimensions still need to be configured and validated.

### Misconception: Direct database connectivity means instant analysis without data work.

Correction: Connectivity reduces some extraction and flattening work. Data quality, semantics, access, mapping, and modeling remain necessary.

### Misconception: Noreja is only a Process Mining visualization tool.

Correction: Noreja combines connectivity, graph-based modeling, causal process analysis, monitoring, custom analysis, contextual knowledge, AI assistance, and related workflows.

### Misconception: Minerva is a general-purpose chatbot with unrestricted access.

Correction: Minerva operates with configured context, tools, permissions, dimensions, and models. Available data and capabilities depend on the customer's setup.

### Misconception: Minerva changes data or acts in source systems on its own.

Correction: according to the Help Center, Minerva only reads; it does not change perspectives, tabs, or dashboards, and it never sees more than the asking user may see. Actions in other systems described on the Platform page (for example triggering a workflow) require human approval and depend on configured tools and the current release.

### Misconception: "Dimension" and "perspective", or "causal hypothesis" and "expected order", are different concepts.

Correction: they are earlier and current names for the same concepts. Current documentation uses perspective and expected order; some screens and older material still use the earlier names.

### Misconception: Noreja has one set of agents.

Correction: "agent" refers to Minerva agents and sub-agents in the product, the ten specialized agents of the Minerva Agent Library, the Minerva Frontier Agents, and the four loop agent types on the Platform page. See section 10 before naming an agent.

### Misconception: An AI-generated explanation is automatically a proven root cause.

Correction: AI output is decision support. A proposed cause should be validated against data, model assumptions, business knowledge, and alternative explanations.

### Misconception: Causal Process Mining automatically proves scientific causality.

Correction: Noreja's causal modeling uses directional process knowledge and relational structure. Claims of causal effect still require an appropriate analytical or experimental design.

### Misconception: All listed modules are included in every package.

Correction: Package inclusions and availability must be checked on the current Pricing page.

### Misconception: All customers use the same LLM or hosting setup.

Correction: Noreja supports configurable model-operation options. The selected setup depends on customer requirements and agreements.

### Misconception: Published customer outcomes are guaranteed.

Correction: Results are context-specific and depend on process scope, maturity, data, implementation, adoption, and organizational conditions.

## 22. Change and Maintenance Policy

This file should be reviewed whenever any of the following changes:

- public product modules or names;
- data-model terminology;
- connector positioning;
- Minerva architecture or model-operation options;
- Frontier Agent, Agent Library, or Minerva agent and skill names or scopes;
- Help Center article URLs (articles are renamed between releases);
- pricing packages or inclusions;
- security or compliance statements;
- public use cases or success stories;
- vendor comparison pages or the classification of a compared vendor;
- canonical URLs;
- German or English site paths.

Recommended maintenance controls:

- store the file in version control;
- generate the displayed review date during deployment;
- run automated link checks;
- compare product terminology with the Platform and Help Center navigation;
- never duplicate current prices or release numbers unless generated from the same source;
- keep `llms-ctx-full.txt` in step: its embedded copy of this file is refreshed automatically before every build (`scripts/sync-llms.ts`), its resource summaries are maintained by hand;
- test representative questions against several LLMs before publishing.

<title>Platform Overview</title>
<content>
The public Platform page presents Noreja as process intelligence on autopilot: a closed loop of four phases, each producing the input for the next. Insights reconstructs a causal process model from system data and works from an anomaly to its root cause; Action turns a finding into an action, such as notifying the responsible role, triggering a workflow, or setting up a redesign, with human approval; Impact calculates potential, investment, and payback per action before the decision; Feedback keeps measuring against the baseline after rollout and restarts the loop if the effect fails to appear. Four generic agent types, one per phase (Insights, Action, Impact, Feedback Agent), hand over to each other, document every step, and can be equipped with a customer's own tools and knowledge bases. The page also links to Minerva 2.0, the Frontier Agents, and the Cost of Inaction calculator. Figures shown on the page are illustrations. The product areas behind the loop are Dashboard, Analyzer, Builder, Workbench, and the AI Hub with Minerva; use the Help Center for what is available in a given release.

<content>

<title>The Expected Order: Perspective Hypothesis, Shortcuts and Backjumps</title>
<content>
This article explains the expected order of a perspective: the activities and relationships that state which activity is expected after which, and against which Noreja compares every case. It covers how to build the expected order in the Builder, how relationships are marked as allowed shortcuts (skipping activities) or allowed backjumps (returning to an earlier activity), and why all of them should be marked. Older material calls the expected order the causal hypothesis or causal model, and earlier documentation described the same ideas as path semantics (conformance, hypothetical, and omitted paths; allowed and prohibited shortcuts and backjumps).

<source>https://docs.noreja.com/en/article/process-patterns-disarray-negligence-rework-and-allowed-deviations</source>
<title>Process Patterns: Disarray, Negligence, Rework and Allowed Deviations</title>
<content>
This article defines the five process patterns Noreja recognises when cases deviate from the expected order. Violations are Disarray (two dependent activities in the wrong order), Negligence (an expected activity skipped, including unexpected start or end activities), and Rework (an activity changed after a later activity had already started). Allowed deviations are Simplification (skipping along a marked shortcut) and Reorder (going back along a marked backjump). The article shows how each pattern is detected, where it appears, and what it usually means for time, cost, and quality.
</content>
</document>

<source>https://noreja.com/en/cost-of-inaction</source>
<title>Cost of Inaction Calculator and Devil's Quadrangle</title>
<content>
This page holds two interactive tools plus explanatory text. The cost-of-inaction calculator estimates the hidden annual cost of an end-to-end process that is not improved: the visitor enters industry, company size, units sold, value per unit, customer base, and production type, the calculator derives the process volumes from those inputs, applies industry-typical benchmarks for manual effort, value leakage, error rates, and variant overhead, and splits the result across the dimensions time, cost, quality, and complexity for one year and for a selectable horizon. The output is an order-of-magnitude estimate from benchmarks, not a measurement of the visitor's own system data, and the whole calculation runs client-side without login or data transfer. The second tool is an interactive Devil's Quadrangle: time opposes cost and quality opposes flexibility, and pulling one dimension outward makes the opposing dimension absorb half of the loss and each adjacent dimension a quarter, because the improvement budget is held constant. A separate control illustrates Noreja's argument that causal process transparency widens the whole frontier instead of only tilting it. The page also carries a seven-question FAQ and a curated list of peer-reviewed sources on the model. Use this page for questions about what unimproved processes cost, about the Devil's Quadrangle, and about the trade-off between process performance dimensions.
</content>

<content>
Generative AI produces content in response to an input and leaves its use to a person; agentic AI uses generative models as a reasoning tool to pursue a goal across steps, call systems, and act. The distinction is the kind of outcome (content versus a changed state), and it implies different safeguards: output review versus permissions, approvals, and action logging.
</content>
</document>

<title>Frontier Agents Definition</title>
<content>
Frontier Agents are AI agents that work towards a goal autonomously and persistently over long periods instead of reacting to individual requests, retaining context and reporting back on their own. The term is not tied to one vendor: AWS used it in December 2025 for autonomous software-development, security, and operations agents, and OpenAI names its enterprise agent platform "Frontier". In Noreja, Minerva Frontier Agents apply the concept to process and knowledge context; see the Frontier Agents product page for current capabilities.
</content>

<document>
<source>https://noreja.com/en/definitions/agentic-process-automation</source>
<title>Agentic Process Automation (APA) Definition</title>
<content>
Agentic Process Automation automates business processes with AI agents that are given goals rather than fixed sequences, working alongside rule-based automation such as RPA and mainly handling exceptions, unstructured input, and judgment calls. Stable standard steps remain deterministic. Effective APA depends on knowing where exceptions occur and what they cost.
</content>
</document>

<document>
<source>https://noreja.com/en/definitions/agentic-process-mining</source>
<title>Agentic Process Mining Definition</title>
<content>
Agentic Process Mining is process mining carried out by AI agents that formulate questions, select analyses, test hypotheses, and report evidence-backed results themselves. It differs from Agent Mining, in which AI agents are the object of analysis rather than the analyst. Agent findings remain analytical results that should be reviewed before acting on them.
</content>

<document>
<source>https://noreja.com/en/definitions/context-engineering</source>
<title>Context Engineering Definition</title>
<content>
Context Engineering is the design of everything an AI model or agent sees at decision time: instructions, data, tools, memory, examples, and rules, in a deliberate structure, order, and amount. It is broader than prompt engineering, and retrieval (RAG) is only one of its techniques. For process questions, the relevant context is structured process data such as cases, objects, timestamps, metric definitions, and responsibilities.
</content>
</document>

<document>
<source>https://noreja.com/en/definitions/human-in-the-loop</source>
<title>Human-in-the-Loop Definition</title>
<content>
Human-in-the-Loop describes AI systems in which a person reviews, corrects, or approves at defined points before the system continues, typically for actions with external effect or high risk. It differs from human-on-the-loop, where the system acts on its own under supervision. The EU AI Act requires effective human oversight for high-risk AI systems.
</content>
</document>

<title>Agent Orchestration Definition</title>
<content>
Agent Orchestration is the coordination of multiple AI agents, rule-based automation, and people within one flow: distributing tasks, handing over intermediate results, managing dependencies, and deciding when a person is involved. It governs how a multi-agent system works together and, unlike classic workflow automation, can adapt the flow at runtime.
</content>

<title>Multi-Agent System Definition</title>
<content>
A multi-agent system consists of several specialized AI agents that together solve a task too large or varied for one agent, often coordinated by a supervising agent. Specialization eases testing and securing individual agents, while handovers, costs, and failure points grow with the number of agents.
</content>

<content>
The Agent2Agent Protocol is an open standard through which AI agents from different vendors communicate and delegate tasks, with each agent describing its capabilities in an agent card. Google introduced it in April 2025 and transferred it to the Linux Foundation. A2A connects agents to each other, whereas MCP connects an agent to tools and data. The definition does not imply that any specific Noreja A2A interface exists.

<content>
AI agent governance comprises the rules, roles, and controls that determine which AI agent may do what: mandate, access rights, approval limits, agent identity, action logging, and regular review. It extends general AI governance because agents act rather than only produce output. The page is educational and not legal advice on EU AI Act obligations.
</content>

<title>Guardian Agents Definition</title>
<content>
Guardian Agents are AI agents that supervise other AI agents during execution, checking actions against goals, rules, and boundaries and, depending on authority, warning, redirecting, or blocking. The term was popularized by Gartner. Guardian agents act at runtime, whereas agent conformance checking examines behavior afterwards.
</content>

<content>
Agent Observability makes visible what an AI agent does in operation, based on traces of every model call and tool invocation, including duration, cost, errors, and output quality; AgentOps is the operating practice around it. Observability shows individual runs in technical depth, whereas Agent Mining aggregates many runs into process patterns.
</content>

<content>
Agentic BPM extends business process management to AI agents that make their own decisions within a process frame, shifting BPM from prescribing steps to setting boundaries and reviewing. The concept was set out in a March 2026 research manifesto by 18 BPM researchers, which names framed autonomy, explainability, conversational actionability, and self-modification as required agent capabilities.

The label concern does not imply that rule-based tools are inferior where they fit.
